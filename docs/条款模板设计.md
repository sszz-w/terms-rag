# 条款模板设计文档

## 1. 基础模板结构

### 1.1 简单条款示例：注册资金

```yaml
id: "registered_capital"
category: "符合性审查"
template: "注册资金不少于 {{minimum_capital}} 万元。"
slots:
  - key: "minimum_capital"
    type: "number"
    unit: "万元"
    label: "最低注册资金"
# 给大模型用的评审指令，告诉它怎么判
review_instruction: "从投标文件中提取注册资金数额，与阈值 {{minimum_capital}} 万元比较。大于等于为符合。"
# 投标文件中应该去哪找对应内容
source_hint: ["营业执照", "企业基本信息", "资格证明文件"]
```

### 1.2 模板组成说明

- **template + slots**：给招标人编制文件用
- **review_instruction**：给大模型评审时用，是条款的"判定逻辑"翻译
- **source_hint**：指导 PDF 解析时去哪个章节提取对应内容

## 2. 复杂条款示例：中国质量奖

### 2.1 场景说明

某个条款内容是：获取过中国质量奖，但隐含信息是必须是由中国的某个部门颁发，级别为国家级非省市级，且时间有效性也需要判定。

**解决方案**：把隐含知识拆成判定规则，无需多次与大模型交互。

### 2.2 模板设计

```yaml
id: "china_quality_award"
category: "符合性审查"
template: "投标人须获得中国质量奖。"
slots: []

# 这里是关键——评审规则不是给招标人看的，是给大模型用的
review_rules:
  - dimension: "奖项名称"
    criterion: "必须是'中国质量奖'或'中国质量奖提名奖'"
    reject_examples: ["省长质量奖", "市质量奖", "质量管理先进单位"]

  - dimension: "颁发机构"
    criterion: "颁发单位必须是国家市场监督管理总局（或原国家质检总局）"
    reject_examples: ["省市场监督管理局", "行业协会"]

  - dimension: "级别"
    criterion: "国家级，非省部级、地市级"

  - dimension: "时效性"
    criterion: "获奖时间在 {{validity_years}} 年以内"
    slot:
      key: "validity_years"
      type: "number"
      default: 5
      label: "有效年限"

review_instruction: |
  逐条检查以下维度，全部满足才判定为"符合"：
  1. 奖项名称是否为"中国质量奖"（含提名奖），排除省市级质量奖
  2. 颁发机构是否为国家市场监督管理总局
  3. 级别是否为国家级
  4. 获奖时间是否在近 {{validity_years}} 年内
  任一维度不满足，判定为"不符合"并说明具体哪个维度不通过。

source_hint: ["荣誉证书", "获奖证明", "企业荣誉", "资质证明"]
```

## 3. 评审 Prompt 示例

### 3.1 完整 Prompt 模板

```
你是一名招投标评审专家，负责对投标文件进行符合性审查。请严格按照评审规则判定，
不要推测或补充投标文件中未明确提供的信息。

## 评审条款

投标人须获得中国质量奖。

## 评审规则

请逐条检查以下维度，全部满足才判定为"符合"：

1. **奖项名称**：必须是"中国质量奖"或"中国质量奖提名奖"。省长质量奖、市质量奖、质量管理先进单位等均不符合。
2. **颁发机构**：必须是国家市场监督管理总局（或原国家质检总局）。省市级市场监督管理局、行业协会颁发的不符合。
3. **级别**：必须是国家级，非省部级、地市级。
4. **时效性**：获奖时间必须在 2021 年 1 月 1 日之后（近 5 年内有效）。

任一维度不满足，整体判定为"不符合"。
如果投标文件中缺少某个维度的信息导致无法判断，判定为"无法判定"。

## 投标文件相关内容

以下内容提取自投标文件，已标注页码：

[第 15 页] 我公司于2022年11月获得第五届"中国质量奖提名奖"，由国家市场监督管理总局颁发，证书编号：ZL2022-XXX。

[第 42 页]
附件：中国质量奖提名奖证书复印件（颁发日期：2022年11月，有效期：长期）。

## 输出要求

请以如下 JSON 格式输出，不要输出其他内容：

{
  "result": "符合 | 不符合 | 无法判定",
  "dimension_checks": [
    {
      "dimension": "维度名称",
      "passed": true/false/null,
      "detail": "判定说明"
    }
  ],
  "reasoning": "综合判定依据",
  "quote": "投标文件中的关键原文",
  "quote_page": 页码数字
}
```

### 3.2 设计要点

- **评审规则用绝对时间**：避免相对时间导致的歧义
- **dimension_checks 数组**：逐维度输出判定，方便前端展示哪个维度通过，哪个不通过
- **投标文件内容已经是筛选过的段落**：减少无关信息干扰
## 4. 输出稳定性问题与解决方案

### 4.1 常见问题

1. **维度名称及 JSON 结构大模型输出不稳定怎么办？**
2. **投标文件筛选方案是否可行？**
   - 计划限制投标人把每个条款数据一一对应到章节，解析章节的内容来组装 prompt

### 4.2 解决方案

**问题 2 的答案**：完全可行。让投标人将条款对应到具体章节，然后解析章节内容组装 prompt 是可行的方案。

**问题 1 的解决方案**：使用结构化输出

#### 方案一：Function Calling（推荐用于多模型兼容）

OpenAI 的 Function Calling 和 Claude 的 tool_use 思路一样，定义 function schema：

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": review_prompt}
    ],
    tools=[{
        "type": "function",
        "function": {
            "name": "submit_review_result",
            "description": "提交条款评审结果",
            "parameters": {
                "type": "object",
                "properties": {
                    "result": {
                        "type": "string",
                        "enum": ["符合", "不符合", "无法判定"]
                    },
                    "dimension_checks": {
                        "type": "array",
                        "items": {
                            "type": "object",
                            "properties": {
                                "dimension": {
                                    "type": "string",
                                    "enum": ["奖项名称", "颁发机构", "级别", "时效性"]
                                },
                                "passed": { "type": ["boolean", "null"] },
                                "detail": { "type": "string" }
                            },
                            "required": ["dimension", "passed", "detail"]
                        }
                    },
                    "reasoning": { "type": "string" },
                    "quote": { "type": "string" },
                    "quote_page": { "type": "integer" }
                },
                "required": ["result", "dimension_checks", "reasoning", "quote", "quote_page"]
            }
        }
    }],
    tool_choice={"type": "function", "function": {"name": "submit_review_result"}}
)

# 解析结果
import json
result = json.loads(
    response.choices[0].message.tool_calls[0].function.arguments
)
```

**关键点**：`tool_choice` 强制模型必须调用这个 function，不会跑偏去输出自由文本。

#### 方案二：Structured Outputs（最严格，仅 OpenAI）

OpenAI 2024年8月推出的功能，JSON Schema 级别的强约束，模型输出 100% 符合 schema：

```python
from pydantic import BaseModel
from typing import Literal, Optional
from openai import OpenAI

client = OpenAI()

class DimensionCheck(BaseModel):
    dimension: Literal["奖项名称", "颁发机构", "级别", "时效性"]
    passed: Optional[bool]
    detail: str

class ReviewResult(BaseModel):
    result: Literal["符合", "不符合", "无法判定"]
    dimension_checks: list[DimensionCheck]
    reasoning: str
    quote: str
    quote_page: int

response = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": review_prompt}
    ],
    response_format=ReviewResult
)

result = response.choices[0].message.parsed  # 直接拿到 Pydantic 对象
```

### 4.3 两种方式对比

| 特性 | Function Calling | Structured Outputs |
|------|------------------|-------------------|
| 输出保证 | 99%+ 符合 schema | 100% 符合 schema |
| 灵活性 | 支持 anyOf、可选字段 | schema 限制更严格（不支持部分高级特性） |
| 用法 | 通用，所有模型支持 | 需要 gpt-4o-2024-08-06 及以上 |

### 4.4 推荐方案

**建议使用方案二（Structured Outputs）**

理由：
- 批量评审场景，输出格式固定
- 100% schema 合规比灵活性更重要
- Pydantic 模型可以直接复用到业务代码里做类型校验

**动态生成 Pydantic 类**：

```python
def build_review_model(dimensions: list[str]):
    DimLiteral = Literal[tuple(dimensions)]

    class DimensionCheck(BaseModel):
        dimension: DimLiteral
        passed: Optional[bool]
        detail: str

    class ReviewResult(BaseModel):
        result: Literal["符合", "不符合", "无法判定"]
        dimension_checks: list[DimensionCheck]
        reasoning: str
        quote: str
        quote_page: int

    return ReviewResult
```
## 5. 多模型兼容性

### 5.1 各家模型支持情况

Structured Outputs 是 OpenAI 的专有特性，它在推理层做了 constrained decoding（受限解码），强制 token 生成只能走 schema 允许的路径。这不是简单的 API 兼容就能实现的。

| 能力 | OpenAI | DeepSeek | 通义千问 |
|------|--------|----------|----------|
| Function Calling（方式一） | ✅ 支持 | ✅ 支持 | ✅ 支持 |
| JSON Mode（基础） | ✅ 支持 | ✅ 支持 | ✅ 支持 |
| Structured Outputs（方式二） | ✅ 支持 | ❌ 不支持 | ❌ 不支持 |

### 5.2 兼容性建议

**如果需要兼容多家模型，统一使用方式一（Function Calling）。**

实际操作中方式一已经足够稳定了，偶尔出现格式异常加一层防御即可：

```python
import json

def parse_review_result(response, expected_dimensions: list[str]):
    raw = response.choices[0].message.tool_calls[0].function.arguments
    result = json.loads(raw)

    # 校验 result 枚举值
    if result["result"] not in ("符合", "不符合", "无法判定"):
        raise ValueError(f"非法 result 值: {result['result']}")

    # 校验 dimension 枚举值
    for check in result["dimension_checks"]:
        if check["dimension"] not in expected_dimensions:
            raise ValueError(f"非法维度: {check['dimension']}")

    return result
```

**解析失败时重试一次即可**，实测 function calling 模式下格式错误率极低（< 1%）。

### 5.3 提高稳定性的技巧

在 system prompt 里加一句：

> "你必须通过调用 submit_review_result 函数返回结果，不要直接回复文本"

配合 `tool_choice` 强制调用，基本不会跑偏。

---

## 6. 总结

### 6.1 模板设计核心要点

1. **简单条款**：使用 template + slots + review_instruction
2. **复杂条款**：增加 review_rules，将隐含知识拆解为多维度判定规则
3. **时间处理**：使用绝对时间而非相对时间
4. **内容定位**：通过 source_hint 指导文档解析

### 6.2 输出稳定性方案

- **单一模型（OpenAI）**：使用 Structured Outputs（方案二）
- **多模型兼容**：使用 Function Calling（方案一）+ 防御性校验
- **错误率**：< 1%，重试机制即可应对

### 6.3 工程实践建议

1. 投标人将条款对应到具体章节，系统解析章节内容组装 prompt
2. 动态生成 Pydantic 模型以适配不同条款的维度
3. 在 system prompt 中明确要求使用函数调用返回结果
4. 添加防御性校验和重试机制
